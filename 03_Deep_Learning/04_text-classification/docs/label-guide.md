# 문의 분류 라벨 정의서

모델의 라벨 코드는 API·DB·대시보드에서 변하지 않는 영문 소문자 코드로 유지한다. 한 문의에 여러 의도가 섞여도 현재 단계에서는 **상담사가 먼저 처리해야 하는 주된 업무** 하나를 지정한다. 판단이 어려우면 자동 배정 대상에서 제외해 상담사 검토로 보낸다.

| 코드 | 포함 기준 | 제외·경계 사례 | 예시 |
| --- | --- | --- | --- |
| `delivery` | 출고, 배송 상태, 지연, 주소 변경, 수령 문제 | 배송 상품의 파손·누락은 `product`; 환불 요청 자체는 `refund` | “배송 조회가 멈췄어요” |
| `refund` | 취소, 반품, 환불 가능 여부·절차·지연 | 결제수단·청구 오류가 별도 라벨로 생기면 그 라벨로 분리 | “반품했는데 환불은 언제 되나요?” |
| `account` | 로그인, 인증, 비밀번호, 회원 정보·탈퇴 | 주문 조회처럼 계정 로그인은 수단일 뿐 배송/환불이 목적이면 해당 업무 라벨 | “휴대폰을 바꿔서 로그인이 안 됩니다” |
| `product` | 상품 정보, 옵션, 재고, 품질, 파손·누락 | 배송 지연·주소 변경은 `delivery`; 환불 절차는 `refund` | “받은 상품 색상이 주문과 달라요” |

## 애매 사례 처리

- “배송이 너무 늦어서 취소하고 싶어요”는 취소·환불 처리 요청이 핵심이면 `refund`, 현재 위치나 도착일 문의가 핵심이면 `delivery`다.
- “상품이 파손됐어요. 환불하고 싶어요”처럼 두 업무가 동등하면 원문을 다중 라벨로 억지로 축소하지 않는다. 현재 단일 라벨 정책에서는 상담사 검토 대상으로 표시하고, 향후 다중 의도 모델 도입 후보로 기록한다.
- 신규 업무가 반복되면 기존 라벨에 억지로 포함하지 않는다. 라벨 정의서·학습 데이터·평가셋을 함께 갱신하고 새 모델 버전을 만든다.

## 라벨링 품질 점검

- 라벨러 2인이 일부 표본을 독립적으로 분류하고, 불일치 사례를 이 문서에 추가한다.
- PII는 라벨링·학습 전에 `[PHONE]`, `[EMAIL]`, `[ORDER_ID]` 토큰으로 마스킹한다.
- 날짜 기반 test에서는 새 표현과 정책 변경으로 인한 성능 저하를 별도로 확인한다.

## AI Hub 첫 실험 매핑

AI Hub 소상공인 주문 질의-응답 데이터에는 현재 `account`에 안정적으로 대응하는 인텐트 묶음이 없으므로, 첫 실험은 아래 3개 라벨만 사용한다. 원본 인텐트 전체를 임의로 네 개 라벨에 맞추지 않는 것이 라벨 노이즈를 줄인다.

| 원본 인텐트 접두어 | 프로젝트 라벨 | 비고 |
| --- | --- | --- |
| `배송_` | `delivery` | 비용·날짜·방법·오류·일반 문의 포함 |
| `교환|반품|환불_` | `refund` | 교환·반품·환불을 하나의 사후 처리 업무로 묶은 첫 버전 |
| `제품_` | `product` | 정보·재고·가격·품질·구성 등 상품 문의 |

매핑은 [aihub-intent-map.json](../configs/aihub-intent-map.json)에서 관리한다. `결제_`, `행사_`, `AS_`, `매장_` 같은 나머지 원본 인텐트는 별도 라벨 정의와 충분한 검토 전까지 제외한다.
